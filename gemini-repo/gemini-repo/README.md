# Research Relay — 私有科研协作中转

赵月全部科研工作共用的多模型协作仓库，不限于写论文：文献调研、讨论画图方案、处理数据、计算、写作、模拟审稿、审查核对等都在这里进行。每个项目一个文件夹（如 `FeCoMn/`），结构和规则相同。新项目照 `_templates/project/` 建立；各模型的入门指令见 `_onboarding/`。

## 角色（2026-11-19 赵月定，所有项目通用）

| 类别 | 成员 | 负责 | 不做 |
|---|---|---|---|
| 网页版对话 | **Claude（主）** | 文献调研与综述、讨论研究思路和画图方案、写作、回复导师与审稿意见、模拟审稿、写任务单和方案文件；**论文等成稿文件的唯一修改者**（Word、插图换图） | 不跑计算、不出图 |
| 网页版对话 | ChatGPT | 与 Claude 权限一致（可读可写仓库，可做 Claude 能做的所有工作），Claude 为主要决策者；首要任务是核查 Claude 的工作。**核查意见可直接写入 review/ 或讨论文件末尾；对其他任何文件的修改，须先在 review/ 写明修改建议，经 Claude 同意后再改（或由 Claude 改）** | 未经 Claude 同意不修改 review/ 以外的文件；不做计算出图 |
| 网页版对话 | Gemini | 暂未接入（无法连接仓库）；需要时上传文件给它核查 | |
| 智能体（本地／命令行） | Codex、Claude Code、Antigravity | 处理数据、计算、出图、查找与提取文献和数据、交付报告；相互核查数据与图 | 不改成稿 Word，不改任务单和方案文件 |
| 决定 | 赵月 | 最终决定 | |

## 常见工作怎么分
| 工作 | 主做 | 核查／补充 |
|---|---|---|
| 文献调研 | Claude 定问题和检索规程，智能体批量检索、下载摘录 | ChatGPT／Gemini 查结论是否准确、有无遗漏；另一智能体抽查引用 |
| 画图方案 | Claude 出方案（discussion/） | ChatGPT／Gemini、智能体提意见；赵月定 |
| 处理数据、计算、出图 | 智能体 | 另一智能体从原始文件复核 |
| 写作与修改 | Claude | ChatGPT／Gemini 查逻辑表达；智能体查数据一致 |
| 模拟审稿 | ChatGPT／Gemini 分别扮审稿人（review/） | Claude 汇总、逐条回应并改稿 |
| 审查核对（投稿前） | 各方按分工 | 赵月定 |

Claude Code 虽名为 Claude，但属于智能体一类。网页版对话的意见直接写入 `<项目>/review/` 或讨论文件末尾，文件名注明来源，如 `review/20261119_intro_ChatGPT.md`；Claude 逐条回应并作决定。

## 交叉核查（通用）
- **智能体三方互查（2026-11-19 赵月定）**：Codex、Claude Code、Antigravity 三个智能体的工作互相核查，谁做的由另外两方之一复核；默认分工（2026-11-19 14:03 赵月调整）：**Antigravity 主做，Claude Code 复核**；Codex 额度恢复后可分担主做，由 Claude Code 或 Antigravity 复核。临时由 Claude Code 主做的任务，改由 Antigravity 复核。复核必须打开原始文件或文献原文，不能凭记忆或只读报告。复核意见写入 review/，并在 STATUS.md 对应任务行注明复核方与结论。
- 自做自查不算核查：谁出的数据或图，由另一个智能体从原始文件复核。
- Claude 写的文字，由 ChatGPT／Gemini 核查逻辑与表达，由智能体核查与数据是否一致。
- 智能体的报告与建议，由 Claude 检查逻辑。
- 意见冲突：各写依据，赵月决定；两方一致不等于正确。

## 通用规则

- 任务编号采用项目前缀加三位序号，如`FeCoMn-T001`。任务放`<项目>/to_agent/`，文件名为`编号_简短标题.md`，例如`FeCoMn-T001_Figure4_redraw.md`。
- 结果放`<项目>/from_agent/<编号>/`，附`REPORT.md`：说明做了什么、所用文件版本、核对结果、遇到的问题及待确认项。
- 每项任务在项目`STATUS.md`占一行，列为编号、标题、负责方、状态、日期、对应文件。状态为待办／进行中／已交付／已确认；交付后更新。
- 提交信息示例：`FeCoMn-T001 done: 简要说明`。
- 不删除、不覆盖已提交的数据、图和脚本。新版本采用新文件名并带日期时间，例如`Figure_4_20261114_2130.svg`。STATUS等状态文件按协作流程更新，由Git保留历史，不改写提交历史或强制推送。
- 每张图必须附生成脚本，以及所用数据的仓库相对路径或SHA256。只交图而不交脚本和数据来源，不算完整交付。
- Word文件只由Claude（网页版）修改。论文每次修改后的新版本放`<项目>/manuscript/`，文件名带日期时间，不覆盖旧版本；该文件夹内说明文件记录各版本的改动。（2026-11-16 赵月确认，取代原来"Word文件不进仓库"的规定）
- 单个文件不得超过50 MB；提交前检查。DFT原始输出、同步辐射原始大文件、波函数等不上传，需要时只放用于画图的处理数据。
- 每次交图提供三份：600 dpi PNG、Arial文字转路径SVG、保留可编辑文字的源SVG。
- 原始资料包规则继续有效：先报告事实和版本差异；不自动删点、不擅自改图或Word；不把CoMn–NC当作现行对照；不混入OER数据。
- 缺文件或存在冲突时如实写入REPORT，不能把旧脚本改名冒充新脚本，不能虚报“零差异核验”。
- 开工前先拉取并读取STATUS和任务；提交前再次拉取，避免覆盖另一方更新。仓库本身不提供自动监听，收到“有新任务／已交付”后读取最新内容。

- 每次上传 Word 成稿时，Claude 同时导出同名纯文本 `<文件名>_plaintext.txt`（正文另附参考文献表 `references_<版本>.txt`），供无法读取 .docx 的模型（如 ChatGPT 连接器）核查；纯文本不含图，上下标与斜体会丢失，需要看图或排版时直接上传 Word 给对方。（2026-11-19 赵月定）

## 空间管理（2026-11-14 增加）

- 中间数据（如 `.npz`、未平滑数组、逐点导出的大 CSV）默认不提交，只在 REPORT 里记录生成方法和 SHA256，需要时由脚本重新生成。确有必要提交时，在 REPORT 中说明理由。
- 预览图只放小尺寸 PNG（宽度不超过约 1600 像素）。600 dpi 正式图每个版本只交一次，不重复上传同一版。
- 原始数据只放一份，后续任务用相对路径引用，不复制。
- Claude 定期检查仓库大小，接近 1 GB 时提醒赵月；届时新建仓库或把已发表论文的文件夹移入归档仓库。
